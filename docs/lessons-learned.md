## Cheat Engine Integration

- `executeCodeEx` internally uses `CreateRemoteThread` — games with thread injection protection will block it silently (returns nil, not an error code)
- **CE's Settings API cannot read a `REG_MULTI_SZ` value — measured 2026-08-04, and `celua.txt` says otherwise.**
  Probed live in CE's Lua console against `HKCU\Software\Cheat Engine`:
  | call | result |
  |---|---|
  | `getSettings()` | ✅ `TLuaSettings` |
  | `s.Value["Recent Files"]` (REG_MULTI_SZ) | string of **length 0** |
  | `s:getBinaryValue("Recent Files")` | **`nil`** — despite `celua.txt:3516` documenting `getBinaryValue(name): bytetable` |
  | `getSettings("Plugins64").Value["00000000 A"]` (REG_SZ, subkey) | ✅ returns the plugin path |
  The control read is the important row: the API, the subkey selection and `Value[]` all work.
  It is the **type** that is unreadable. Use `io.popen('reg query …')` for a MULTI_SZ — measured working,
  and note `reg.exe` renders the entry separators as the **literal two characters** `\0`, not real NULs.
  **The general lesson, which cost three probe rounds:** for CE, "documented in `celua.txt`" is a
  hypothesis, not a verification. Probe it in the Lua console before building on it.
- **A CE table script cannot learn its own `.CT` path.** No API returns it — not `getSettings`, not
  `TrainerOrigin` (trainer-launch only), not `findTableFile`/`createTableFile` (those are for files
  *embedded in* the table), and not the File menu (recent tables live under a `Load Recent` **submenu**,
  so they are not reachable as File-menu children). `getMainForm().OpenDialog1/SaveDialog1.FileName` are
  proxies that only `File > Open` / `File > Save` fill in — a double-click or a recent-files pick leaves
  both empty. If a script needs a sibling file, have something outside CE record the folder.
- **`executeCodeEx`'s real signature — verified against CE's own `celua.txt` (2026-08-04), because every earlier statement of it in this repo was wrong:**
  `executeCodeEx(callmethod, timeout, address, params...)` where **`callmethod` 0=stdcall / 1=cdecl**, **`timeout`** is milliseconds (`nil` or `-1` = wait forever; **`0` = don't wait AND don't free the call memory — a leak**), and **`address` is argument 3**.
  Two traps this caused: passing the address in slot 2 makes CE run with `address = nil` and **return `nil` with no Lua error**, which `pcall` reports as success; and "fixing" it by dropping a `0` into the timeout slot swaps a dead call for a memory leak. The only historically correct call site is `scripts/ue5_dissect.lua:44`.
- **Don't use `executeCodeEx` to call a DLL export and read its return value — use the mailbox (shared memory) instead.** The whole CE↔DLL surface goes through the Mimic single-slot mailbox (`g_invokeMailbox`): CE only does `writeQword`/`readInteger` (= Write/ReadProcessMemory) against the struct, the DLL polling thread executes (and dispatches ProcessEvent to the game thread). That's why `invokeUFunction` and `setDebugCamera` (CMD_SET_DEBUG_CAMERA) use the mailbox, not `executeCodeEx`. See `docs/CE-Bugs-Minesweeper.md` §5 for the related "embedded helper stays cached" gotcha.
  > **Caveat added 2026-08-04, and worth knowing before citing this rule as evidence.** The original justification recorded here was *"even a no-parameter export call (`executeCodeEx(timeout, nil, addr)`) came back `nil`, so return-value capture is unreliable"*. That example is **itself a malformed call**: it puts a timeout value in the `callmethod` slot, which is only valid as 0 or 1. So the observation may have measured a bad call rather than an unreliable API — the same defect audit #4 B1 later found shipped in both CE script generators and in `UE5CEDumper.CT`. The mailbox decision still stands on the **independent** reason above it (`CreateRemoteThread` is silently blocked by thread-injection protection in some games, and that is directly observed), but do not cite the returns-`nil` experiment as proof of anything until it is re-run with `(callmethod, timeout, address)` in the right order.
- CE `File -> Open` vs `File -> Save` update **different** dialog objects (`OpenDialog1` vs `SaveDialog1`)
- `getCheatEngineDir()` returns CE root (e.g., `C:\Program Files\CE 7.5\`) — DLL must be placed next to the CT, NOT in a subdirectory
- **CT Lua DLL path search**: Try `OpenDialog1.FileName` first, fall back to `SaveDialog1.FileName`, then `getCheatEngineDir()`
- **CE XML hierarchical tree addressing model**: Each child's Address is relative to its parent's **RESOLVED** address. Pointer fields use `Address=+{offset}, Offsets=[0]` (CE dereferences). Inline fields use `Address=+{offset}` with no Offsets. Leaf fields ALWAYS use just `Address=+{offset}` — parent's `Offsets=[0]` already handled the deref. Never do `Address=+0, Offsets=[fieldOffset]` (double-deref bug).
- **CE XML TArray addressing**: Array group: `Address=+{fieldOffset}, Offsets=[0]` dereferences `TArray.Data`. Elements: `Address=+{N*elemSize}` — simple offset from already-dereferenced data pointer, NO Offsets needed.
- **CE XML type mapping**: `IntProperty/Int8/16/64` → `ShowAsSigned=1`; `BoolProperty` with bit mask → Binary type (`BitStart + BitLength=1`); pointer `ObjectProperty` → `ShowAsHex=1`

## Memory & Validation

- **Always add memory hex dumps in validators** — invaluable for diagnosis when running blind inside a game process
- **`strstr` in validators is dangerous**: It ignores null terminators within the buffer, allowing matches across garbage bytes. Always use `strcmp` with exact length checks in security-critical validation paths.
- **`LooksLikeHeapPtr` is insufficient for rejecting 32-bit flag values on x64**: Values like `0x40000000` (EObjectFlags::Const, ~1GB) pass all three checks. On x64 Windows with ASLR, real heap pointers are typically > 4GB (`0x100000000`). When strong pointer validation is needed, add a magnitude check (< 4GB → suspicious) plus a `ReadSafe` dereference check.
- **ValidateGObjects must validate the chunk chain, not just NumElements**: The upper 32 bits of a code-section pointer (e.g., `0x00007FF7` = 32759) can coincidentally fall in the valid NumElements range. Must also verify: (1) Objects pointer can be deref'd, (2) chunk[0] is a heap pointer (not in game module).
- **V12/RE2 pattern resolution**: RE-UE4SS signatures resolve to the ObjObjects field, then subtract 0x10 to get struct base. This is `target - 0x10` (no deref). Doing `*(target) - 0x10` is wrong (deref-then-subtract).
- **Build scripts should always force clean builds**: CMake incremental build can miss source changes. Delete `build/` before cmake configure, `bin/obj/` before dotnet build.

## FName / FNamePool

- **AOB patterns for GNames must be context-specific for newer UE builds (UE5.5+)**; use pointer-scan fallback as primary for UE5.5+
- **GNames address `[addr]=0` is normal**: FNamePool is an inline struct in `.data`, not a pointer-to-pointer. `[GNames]` reads FRWLock (first 8 bytes), which is 0 when unlocked. Actual name data is at `GNames+0x10` (Blocks[]).
- **UE4 TNameEntryArray vs UE5 FNamePool**: Completely different data structures. UE4: double-deref (array→chunk→entry), 16384 entries per chunk, string at fixed offset. UE5: packed inline entries with 2-byte header, single deref, header encodes length.
- **Hash-prefixed FNameEntry (UE4.26 SE fork)**: Some builds prepend a 4-byte ComparisonId before the 2-byte header: `[4B hash][2B header][string]`. Validators must try header at both offset 0 and offset 4. Diagnostic clue: "None" appears at offset +6 from chunk pointer.
- **Hash-prefixed FNameEntry stride = 4, not 2**: `alignof(FNameEntry)` becomes 4 (due to uint32_t member). The index-to-byte offset conversion must use `offset * 4`. Diagnostic clue: names like 'operty' (tail of 'Property').
- **FName index 1 can be invalid**: FName indices are byte_offset / stride, not sequential. Index 1 (byte offset 2 with stride=2) falls INSIDE entry[0]'s "None" string. Don't use FName[1] as a diagnostic indicator.
- **An invalid FName INDEX renders as believable junk = GIGO, not a decoder bug** (Elliot UE4.27, build 1481): an uninitialized 4-byte `NameProperty` value (e.g. `ComparisonIndex=2`) lands mid-`None` in a packed FNamePool, so the ANSI decode concatenates the `None` tail + adjacent packed-entry header bytes + the engine-intrinsic names they sit next to → `??ByteProperty??IntProperty` (the `??` are sanitized header bytes). The stride/offset math is correct for every REAL name (index*stride = its own [2B header][string] boundary by allocator construction). **Diagnostic rule**: a believable-but-wrong NameProperty value that concatenates property-type tokens (`ByteProperty`/`IntProperty`) means the source FName INDEX is junk (upstream), NOT a stride bug — check the index is a valid entry boundary before re-investigating the decoder. **Fix** = `Utf8Helpers::SanitizeAnsiName` (ANSI sibling of `IsImplausibleWideName`): a real narrow FName is pure printable ASCII, so the FIRST non-`[0x20,0x7F)` byte (≠ NUL) is decisive → return `""` so `Serie::GetString` (both ANSI + UE4 paths) yields a miss and callers render `None`. A literal `?` (0x3F) is printable and preserved. **No threshold** (a length/density gate under-fires: the junk run is dominated by printable name tokens, only ~14% `?`). Harm was cosmetic only (len≤1024 cap + SEH, `?` is XML-safe, never reaches a CE symbol). Sibling of the DQ3 HD-2D backward-scan mojibake fix.
- **FNamePool should be initialized before ObjectArray**: This enables using FName resolution as the primary validation signal for FUObjectItem stride detection — nearly impossible to get false positives.
- **`ValidateGNamesAny()` wrapper**: Tries FNamePool→Structural→UE4 validators in sequence. Single call site makes code DRYer and ensures new validators are automatically tried.

## ObjectArray / Stride Detection

- **FUObjectItem item[0] can be null**: GObjects arrays often have null in slot 0 (especially UE4). `DetectItemSize` must scan forward — don't require item[0] to be valid.
- **Anchor-scan is fragile**: Scanning chunk bytes in 8-byte steps to find a "first valid pointer" produces false positives. Correct approach: walk at stride-aligned positions only (`offset = idx * stride`, starting from 0) and validate with FNamePool string resolution.
- **LCM alignment creates false positive strides**: For true stride S, probing with stride S' finds valid items at positions that are multiples of `LCM(S, S')`. For S=24 and S'=16, LCM=48 → every 3rd 16-byte position coincidentally aligns. Always add a tiebreaker (fewer bad items = correct stride).
- **Early exit bias**: `if (outNamed >= 5) break` makes all strides stop at the same named count when LCM alignment provides enough matches. Remove early exit; scan all items equally to reveal the true signal via bad counts.
- **Bad items are the strongest stride signal**: Correct stride reads valid data (objects or null) at every position. Wrong strides read misaligned garbage at most positions. Scoring: `named * 10 - bad * 3`.
- **Some UE4 builds use flat (non-chunked) GObjects arrays** (UE4.11–4.20): Instead of `FUObjectArray → chunk** → chunk[] → FUObjectItem`, the array is `Objects* → FUObjectItem[]` directly. Detection: check if `*(Objects + 8)` is a valid heap pointer when `numElements > OBJECTS_PER_CHUNK`. If not (e.g., `0x40000000` = EObjectFlags), the array is flat.
- **Flat array detection must happen BEFORE chunked probing**: Chunked Phase 1 can accidentally find valid items via LCM alignment when reading UObject internal memory, masking the flat layout.
- **EObjectFlags 0x40000000 = Const**: In UE4's FUObjectItem, the Flags field at item+0x08 can contain `0x40000000` (RF_Const). Reading flat item[0].Flags as "chunk[1]" gives a flag value that correctly fails strong pointer checks.
- **OctoPath Traveler uses stride 16 (not 24)**: Despite being UE4, FUObjectItem is 16 bytes. The stride depends on whether the engine was compiled with GC clustering support.
- **DetectLayout must validate Objects pointer**: Always validate that `*(addr + objectsOffset)` is a heap-like pointer — not null, user-mode range, NOT in the game module's code section.
- **UE4 FUObjectArray has extra members before ObjObjects**: Fields like `ObjFirstGCIndex`, `ObjLastNonGCIndex` can appear at offsets 0x00–0x0C, pushing `ObjObjects.Objects**` to +0x10.
- **Pagination: advance by scanned, not returned**: When the DLL skips unnamed/null objects, the UI must advance by the number of indices **scanned** (`scanned` field), not by objects returned. Otherwise pagination stalls or loops infinitely.
- **`MaxElements` is a capacity, not a population — never bound it by what a game "should" have** (build 2782, DragonSword Awakening). `MaxElements = MaxChunks * 64K` tracks the title's `gc.MaxObjectsInGame` ceiling; a generous one is normal. The old `maxElements > 0x800000` (8.4M) sanity cap rejected the CORRECT preset on a title with `MaxChunks=161` → **10,551,296**. Bound this slot only loosely enough to reject a *pointer half* (the value it holds when the offset is wrong — MindsEye: 233M).
- **A rejected-correct preset does not fail loudly; it falls through to a wrong one that looks healthy.** When the strict tier rejected UE5-Extended above, the relaxed tier accepted row B and logged `relaxed B, Num=37099` as a success. Rows B and E both read Objects from **+0x10**, so pointer + cyclic-class-chain validation cannot separate them — first-listed wins. On a UE5-Extended array B's `numOff` (+0x04) is **`ObjLastNonGCIndex`**: in range, self-consistent, and permanently frozen at the startup disregard-for-GC high-water mark. Result: 37,099 of 317,810 objects enumerated, all of them CDOs/startup assets, and every runtime object invisible to every scan.
- **Discriminate ambiguous layout rows by a field the wrong row must get wrong — don't reorder them.** B's own chunk counts (`MaxChunks@+0x08` / `NumChunks@+0x0C`) are real on a genuine B layout, but on UE5-Extended +0x0C is `OpenForDisregardForGC`, a bool that reads 0 after startup — so `numChunks >= 1` rejects B there and cannot reject a real B. Reordering E ahead of B would only move the theft: E's +0x20/+0x24 reads could then steal a real Back4Blood array.
- **The tell for a mis-latched array layout is a live counter that never moves.** `GetCount()` re-reads memory every call, so a genuine `NumElements` fluctuates constantly. Identical counts across map loads and 78 minutes of play mean the offset points at something frozen, not that the game is idle. Cheap confirmation, no rebuild needed: `find_by_address` on a known-live object — `index: -1, match_kind: "backward"` means the object is NOT in the enumerated range, while a CDO returning `match_kind: "exact"` proves the array itself is fine.

## UE Offsets & Version Detection

- **CasePreservingName**: FName grows from 0x8 to **0xC** bytes (adds DisplayIndex — three int32, alignof 4,
  **no trailing pad**), and the UObject `NamePrivate`→`OuterPrivate` **slot** grows 0x8 → **0x10** because
  `OuterPrivate` is an 8-aligned pointer. Those are two different numbers and conflating them was a whole
  defect family (audit A9): use 0x10 for a slot or a `TPair<FName, 8-aligned-T>`, and 0xC for a packed
  `FName[]` stride, a step to an adjacent FName, `FScriptDelegate`, or anything compared against an
  engine-reported `ElementSize`. Never hardcode either — detect dynamically.
- **Dumper-7 reference patterns**: `FindFFieldNameOffset()` brute-force probing, `FixupHardcodedOffsets()`, `InitFNameSettings()` — gold standard for dynamic offset discovery.
- **"rty" diagnostic pattern**: When field names show truncated type names (e.g., "rty" from "Property"), Name offset is wrong and reading into adjacent FFieldClass data. Type names correct but field names wrong = ClassPrivate offset OK but Name offset shifted.
- **Version detection needs context**: Bare version patterns like "5.6." appear in game data. Three-tier approach: (1) exact `++UE5+Release-` prefix, (2) `Release` in preceding 16 bytes, (3) bare pattern with guard against preceding digit/period.
- **FProperty-to-UProperty fallback**: When FProperty scan fails in `ValidateAndFixOffsets`, retry with UProperty scan. This auto-corrects the mode even with wrong version detection.
- **RE-UE4SS CustomGameConfigs are ground truth for UE4 offset validation**: Use `MemberVariableLayout.ini` as reference only — don't consolidate per-game configs into UE5CEDumper. Our DynOff auto-detection already discovers correct offsets dynamically.
- **UE4.18 uses FNamePool, not TNameEntryArray**: Don't assume UE4 = TNameEntryArray. FF7R (Square Enix UE4.18 fork) uses standard FNamePool.
- **A UE major-version bump can be 100% layout-identical — diff data members, not line count** (UE6.0 readiness, verified `origin/5.8..origin/ue6-main` 2026-06-30): every dumper-critical structure (FUObjectArray/chunked array, FUObjectItem, UObjectBase, UStruct/UClass, FProperty/FField, FName/FNamePool) is byte-identical between shipping UE 5.8 and 6.0 — the 100+ line 6.0 header diffs are almost all `AUTORTFM_*` annotations and virtual-signature churn (`PostLoad(Object)`), adding zero data members. **Diagnostic rule**: a big header diff is NOT proof of layout change — grep for actual *data members* added/removed and for `#if`-gated members before touching any offset. The one real risk is a conditionally-compiled member: UE6 adds `FRemoteObjectId` to UObjectBase + FUObjectItem ONLY `#if UE_WITH_REMOTE_OBJECT_HANDLE` (experimental multi-server/UEFN, OFF in shipping); if ever ON it shifts Class/Name/Outer and forces FUObjectItem packing off. (The "UE6" FUObjectArray cache-locality reorder actually shipped in **5.8**; our `"UE5.8"` preset already covers both.)

## GWorld

- **GWorld null is common in UE4**: Many UE4 games have `*GWorld == 0`. The DLL's `walk_world` has a GObjects fallback that searches for a UWorld instance.
- **GObjects fallback for GWorld should skip CDOs**: Filter by checking if object name starts with `"Default__"`. CDOs have all instance pointers null, producing misleading empty results.
- **GWorld `[addr]=0` doesn't mean broken**: GWorld IS a pointer-to-pointer, but `*GWorld` can be 0 during loading screens or when AOB found wrong address.
- **DLL partial-success responses need UI error handling**: When the DLL returns `ok=true` with an `"error"` field, the UI must read and display it. Always propagate error fields through the model to the ViewModel.

## Logging

- **Log structure matters for AI analysis**: Splitting by phase (scan vs pipe) + adding category tags + SUMMARY level reduces analysis from reading 2MB to `grep "[SUMMARY]"` → 3 lines.
- **Per-process mirror logging aids cross-session comparison**: Writing logs to both `Logs/` and `Logs/<ProcessName>/` allows comparing current vs previous runs.
- **Build system**: VS 2026 (v18) at `C:\Program Files\Microsoft Visual Studio\18\Community`. Use a temp `build.bat` calling `vcvarsall.bat amd64` then cmake — bash→cmd quoting for paths with spaces is fragile. Delete after build.

## UFunction Invoke / ProcessEvent

- **Vtable-index detection for ProcessEvent is unreliable** (discovered build 647, fixed build 648). The original `DetectProcessEventVTableOffset` in `dll/src/Frieren.cpp` picked the slot purely from a hardcoded UE-version table and "validated" by checking that `vtable[offset]` points to readable code -- which every entry does, so the check was a no-op. On both ES2 (UE 5.5, slot 0x220) and Geri (UE 4.27, slot 0x218) the resulting hook landed on **a UObject virtual adjacent to ProcessEvent**. Build 2399 identified it exactly from the DropIn 4.27.2 PDB: `vtable+0x218` is slot 67 = **`UObject::OverridePerObjectConfigSection`**, one slot before ProcessEvent — an empty base stub, which is why the symptom was "invoke does nothing" rather than a crash. (It is *not* `CallFunction`: `UObject::CallFunction` is not virtual and occupies no vtable slot at all.) Symptoms that surfaced live: instance-method invokes always time out at `-5` (game thread is busy firing PE many times/sec but our queue never drains -- hook isn't on PE); static-native fast path "succeeds" with `return=0` because the wrong vtable slot has a compatible-enough ABI to not AV but doesn't write anything useful. Build 648 fix: function-body pattern scan (modeled on Dumper-7 `vendor/Dumper-7/Dumper/Engine/Private/OffsetFinder/Offsets.cpp:15-74`) — iterate vtable slots in `[0x100, 0x300]`, find the slot whose function body contains two `TEST [reg+disp32], imm32` instructions with `imm32 = 0x00000400` (FUNC_Native) and `imm32 = 0x00400000` (high-flag mask). This identifies ProcessEvent by what it *does*, not where it *sits*. The version-table heuristic is retained as a `LOG_WARN` fallback.
- **Validate hooks by side-effect, not by metadata** (build 648). Pre-build-648 the "did the hook install correctly?" check was "does the function pointer look readable" — a metadata test that every UObject virtual passes. The fix that actually matters is the *side-effect* test: `Stark` now exposes `GetHookFireCount()` (atomic, ticked at the top of `HookedProcessEvent`), and `Frieren::TryInstallGameThreadHook` spawns a detached 1500ms validator thread that logs a loud `[ERROR] GameThreadDispatch: VALIDATION FAILED` if the counter is still 0 when it wakes up. UE's real ProcessEvent fires many times per second during normal gameplay, so a zero reading after 1.5s is high-confidence evidence of a wrong hook. **General lesson**: when installing any hook on a high-traffic function, instrument a counter and assert it ticks within a known time window. The silent-failure mode where "install succeeded but we hooked the wrong thing" is the precise reason a 600+ build bug slept undetected — refuse to ship that failure mode silently again.
- **`FProperty::PropertyFlags` is at `ElementSize + 4`, NOT `+8`** (build 642 fix in `dll/src/Genau.cpp`). UE source layout puts `ArrayDim` BEFORE `ElementSize`, not between `ElementSize` and `Flags`. The wrong `+8` formula reads the high 32 bits of the 64-bit Flags + adjacent fields, which silently nukes the parm-classification bits (`CPF_Parm=0x80`, `CPF_OutParm=0x100`, `CPF_ReturnParm=0x400`) that all live in the low 32. Symptoms: every UFunction parameter classified as `IsReturn=false` / `IsOut=false`. The bug was silent for years because almost no UI flow cared about the classification — it surfaced only when build 637's Verify Return Value mode tried to find the return slot.
- **~~KismetMathLibrary helpers are stubs in cooked Shipping~~** — **RETRACTED build 648**. The "stub returning 0" pattern was 100% a side-effect of the build-647 wrong-vtable-slot bug, not a cooker artifact. Live test 2026-05-11 on ES2 (UE 5.5) with the build-648 pattern scanner picking `vtable+0x278`: `Add_IntInt(3,4)=7`, `Multiply_DoubleDouble(3,4)=12`, all correct. **General lesson**: when a UFunction invoke "succeeds" (`result=0`) but the return value reads zero / unchanged, the FIRST suspect is wrong-hook-target, not a cooker stub. Reach for `Stark::GetHookFireCount()` to verify the hook actually ticks under normal gameplay before blaming the function itself. Don't propose new "this UFunction class is also a stub" hypotheses without first confirming the hook is firing.
- **`FUNC_Native | FUNC_Static` UFunctions are safe to call off-thread**: build 636 added a fast path in `Mimic::HandleInvoke` that bypasses `Stark::EnqueueInvoke` when both flags are set. These are pure helpers (KismetMath / KismetString / KismetArray / KismetSystem libraries — when they're not BP-FastCall-stubbed) with no `this` state, so `ProcessEvent` from the pipe thread is safe and side-effect free. Without the fast path an idle game (main menu, no PE traffic) leaves the queue undrained until the configured deadline expires (`-5` timeout). Stateful methods (BP events, RPCs) still route through `EnqueueInvoke` unchanged.
- **CE Lua `getAddress` vs `getAddressSafe`**: `getAddress(name)` throws / returns garbage when the symbol isn't in CE's module symbol table; `getAddressSafe(name)` returns nil/0. For DLL exports like `g_invokeMailbox`, also try the module-prefixed form (`'UE5Dumper.g_invokeMailbox'`) — some user setups only register the prefixed variant. The mailbox-resolution helper inside `ue5_invoke_helper.lua`'s `findMailbox` does both; any code reaching outside the helper (e.g. inline diagnostic dumps in generated AA Scripts) must mirror that pattern.
- **CE `tableFile.Stream.write(string)` silently drops content on some payloads**: Discovered when building the Tools -> Inject Helper feature (build 611 -> fix 3fc4d8c in AOBMaker repo). `f.Stream.write(content)` returns no error but `f.Stream.Size` keeps reading 0 immediately after, so any size-verify check fails. The reliable population pattern (used by CE's own `autorun/java.lua`) is `createStringStream(content)` + `f.Stream.copyFrom(ss, 0)` + `ss.destroy()`. Apply this for any TableFile-from-Lua-string scenario.
- **AA Script generation should use `ElementSize+4`-derived flag offsets across the board**: Anything that walks UFunction parameters and reads PropertyFlags must use the corrected offset. Sweep search: `propFlags`, `PropertyFlags`, `CPF_` references in DLL code (Ubel.cpp + Aura.cpp + Mimic.cpp).
- **`Ubel::WalkFunctions(classAddr)` is NOT inheritance-aware — walk the Super chain to find inherited engine UFunctions** (Teleport build 1035 fix). `WalkFunctions` only enumerates a single UClass's OWN `Children` chain. Engine BlueprintCallables like `K2_SetActorLocation` / `K2_TeleportTo` (AActor), `SetControlRotation` / `StopMovement` (AController), `StopMovementImmediately` (UMovementComponent) are declared several levels ABOVE a game's concrete pawn/controller subclass, so a single `WalkFunctions(pawnClass)` never finds them. Symptom: the teleport `K2_SetActorLocation` lookup missed on every game, silently fell to the tier-2 raw `RelativeLocation` write (which CharacterMovement overwrites each tick), so "recall did nothing". It worked for Debug Camera ONLY because `ToggleDebugCamera` is declared on `UCheatManager` itself. **Fix**: `Wirbel::FindFunc` climbs `class → DynOff::USTRUCT_SUPER → …` until found. **Rule**: any reflection lookup of an engine base-class UFunction MUST walk the super chain — the per-class `WalkFunctions` is only correct when the function is declared on that exact class.
- **A successful `K2_SetActorLocation` invoke can still visibly do nothing in click-to-move ARPGs** (Titan Quest II, build 1035). The engine call returns `rc=0` / `ReturnValue=true` and the pawn IS moved, but the controller's PathFollowing/click-to-move system walks it straight back to the commanded destination on the next tick. **Mitigation**: after teleporting, also invoke `AController::StopMovement()` on the PlayerController (aborts the active move order) in addition to `UCharacterMovementComponent::StopMovementImmediately()` (zeroes velocity). Both best-effort. 3rd-person action games (SEED Battle Destiny) don't need it; ARPGs do. This is the game-specific "may snap back" the tier model warns about — log the invoke result so you can tell "invoke failed" from "invoke succeeded but the game re-asserted".
- **Some cooked games strip `AActor::K2_SetActorLocation` / `K2_TeleportTo` from reflection — teleport via the ROOT COMPONENT's `K2_SetWorldLocation` instead** (Octopath Traveler / SE HD-2D, build 1042). Log: `no K2_TeleportTo / K2_SetActorLocation on pawn class — raw-write fallback`, yet `AController::StopMovement` + `StopMovementImmediately` (also inherited) WERE found — proving the super-chain walk works and these two specific actor-level setters were genuinely cooked out (UE strips BlueprintCallable UFunctions no cooked Blueprint references). ## Proxy DLL Deploy

- **Three UE shipping layouts to handle, not two** (build 691 + 692 Satisfactory + StellarBlade/NMKART/Palworld/TQ2 fix). Real-world Steam libraries surface three distinct patterns:
  - **Monolithic** (most games — DQ7R, Hogwarts, Stray, ES2…): real exe in `<Game>\<Sub>\Binaries\Win64\<Game>-Win64-Shipping.exe`; `<Game>\Engine\Binaries\Win64\` holds **only** `CrashReportClient.exe`.
  - **Hybrid** (StellarBlade, NMKART, Palworld, Titan Quest II): real exe in `<Game>\<Sub>\Binaries\Win64\<Game>-Win64-Shipping.exe` **AND** a stub launcher exe at `<Game>\Engine\Binaries\Win64\<Game>-Win64-Shipping.exe`. Both look like valid UE shipping exes — a "skip known stub names" filter (CrashReport) can't tell them apart because the stub launcher has the *same name* as the real exe.
  - **Pure modular** (Satisfactory): NO .exe in `<Game>\<Sub>\Binaries\Win64\` at all (only `.modules` manifest + game-side DLLs). Real launcher (0.3MB stub) lives at `<Game>\Engine\Binaries\Win64\<Game>-Win64-Shipping.exe` alongside the engine DLLs (CoreUObject, etc.).
- **Solve with a two-tier search, not a more-clever stub filter**: walk primary roots (gameDir + non-Engine subdirs) first; only fall through to `<Game>\Engine\Binaries\Win64\` when primary contributed zero rows for that gameDir. Monolithic wins on primary (and never walks Engine, so no phantom CrashReport). Hybrid wins on primary (and never walks Engine, so no phantom stub launcher). Pure modular has nothing in primary, falls to Engine, picks the real launcher. The build 691 first attempt (walk Engine unconditionally + filter CrashReportClient by name) was insufficient because the stub-launcher exe in hybrid layouts has the same filename as the real game exe.
- **`version.dll` placement: drop next to the .exe the UI surfaces**, NOT next to the game's DLL folder. Hybrid builds typically have an empty-ish `<Game>\<Sub>\Binaries\Win64\` that the user assumes is "the game" (because the folder name matches the game's name) but the launcher exe lives elsewhere. Always trust where the OS process gets its working directory from — the loaded .exe's folder — not where intuition says the proxy should sit.
- **Multi-module AOB scan (`Macht::AOBScanAllModules`) handles modular UE on the dump side**, but proxy deploy is the orthogonal half — even if the DLL would find GObjects in `CoreUObject-Win64-Shipping.dll` post-injection, the DLL never loads in the first place if `version.dll` is in the wrong folder. The 15-game corpus already contained `FactoryGameSteam`'s 4,868 BPGCs cleanly — proving the scan side works once we get loaded — so the issue was always proxy-deploy detection, not scanning.
- **EA-launcher games block both `version.dll` and `dinput8.dll` proxy preloading** (build 704 *Star Wars Jedi: Fallen Order* lesson — UE 4.21, install path `H:\SteamLibrary\steamapps\common\Jedi Fallen Order`). The install puts two **identical 58.4 MB** exes side-by-side in `SwGame\Binaries\Win64\`: the canonical UE name `SwGame-Win64-Shipping.exe` plus a renamed copy `starwarsjedifallenorder.exe` that EA's launcher actually targets. CE sees the running process name as the latter. **Neither proxy DLL is loaded** by the wrapped process — EA's launcher applies `SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_SYSTEM32)` (or equivalent) before spawning the UE binary, stripping the exe's own directory from the DLL search path so version.dll / dinput8.dll dropped alongside it never resolves. Scan side itself works fine once the DLL is inside the process — GObjects / GNames / GWorld all resolve cleanly via CE manual injection. **Action**: document CE injection as the workaround in the UI's Proxy Deploy panel error state for any title where proxy deploy "succeeds" (file copied) but the pipe never connects after game launch. Likely also affects other EA App / Origin / Ubisoft Connect / battle.net launcher titles — keep an eye out and accumulate the list. Don't try to "fix" the proxy side — it's outside our control; the launcher is the one stripping the search path.

### Windows filesystem traps, measured while building leftover-proxy cleanup (build 2525)

The first directory-deleting feature in the app. Every one of these was **measured on a real machine**,
and each makes the obvious implementation dangerous. They generalise well beyond this feature.

- **`EnumerationOptions` silently hides Hidden and System entries.** `new EnumerationOptions()` defaults
  to `AttributesToSkip = FileAttributes.Hidden | FileAttributes.System`. Measured: a folder holding
  `version.dll` plus a `+h +s desktop.ini` enumerated as **2 entries via the bare
  `Directory.EnumerateFileSystemEntries(path)` overload and 1 via the `EnumerationOptions` overload**.
  For a delete predicate that turns "this folder holds someone's hidden save" into "this folder holds
  only our DLL". **Use the bare overload whenever the answer decides a deletion.**
- **`Directory.Enumerate*` is LAZY, so `catch { }` around a `foreach` yields a PARTIAL list that is
  indistinguishable from a complete short one.** This is the more dangerous half of the trap because the
  surrounding code's own idiom (`ProxyDeployService.cs`, several places) IS `catch { }` — correct for a
  SCAN, catastrophic for a DELETE. Materialise inside the `try` and treat any exception as "unknown",
  never as "empty".
- **`File.Delete` through a junction destroys the TARGET's file.** With `Win64` as a junction to a real
  folder, enumeration listed the target's contents as if they were local, and deleting "our DLL" there
  removed the real file inside the target. Check `FileAttributes.ReparsePoint` **before** touching
  anything, and refuse rather than resolving the target.
- **`Directory.Delete(path, recursive: true)` on a folder containing an unvalidated junction removes the
  junction and THEN throws `UnauthorizedAccessException`** — a half-completed operation the caller
  believes did nothing. Prefer the **non-recursive** overload walked one level at a time: it throws
  unless the directory is genuinely empty, which is a kernel-enforced emptiness check no pre-computed
  plan can fake, and it closes the check→confirm→act race for free (anything created in between simply
  makes that step throw and the walk stops).
- **`FOF_ALLOWUNDO` on a volume with no recycler silently HARD-deletes.** So a "moved to the Recycle Bin"
  promise must be guarded by `DriveInfo.DriveType == DriveType.Fixed`, and refusing is the right
  behaviour — never fall back to a permanent delete.
- **Verify a recycle actually recycled.** `SHFileOperationW` returning 0 and `File.Exists == false` is
  ALSO what a hard delete looks like. Proven properly by counting `Shell.Application.Namespace(0xA)`
  before/after (measured 34 → 35, item found by name). A struct-marshalling error would give `rc=0x57`.
- **`Path.GetFileName` returns `""` for a path with a trailing separator**, so a shape test like "is this
  folder named Win64" silently fails on `C:\a\Binaries\Win64\`. Trim separators first.
- **Deleting a directory can fail for two unrelated reasons that must not be reported as one.**
  `IOException` = still has something in it (expected, the whole point). `UnauthorizedAccessException` =
  it may well be empty and we simply may not remove it. Collapsing them sends the user hunting for a
  file that is not there.

## Pipe Protocol / Batching

- **Two distinct optimisation wins exist when batching pipe reads**: (1) **pipe round-trip amortisation** — N calls share one envelope, saves N × ~0.3ms latency + JSON envelope cost; (2) **shared-state amortisation** — when each call would otherwise re-walk an expensive data structure (e.g. GObjects), batching collapses N walks into one. The build-685 `search_properties_batch` got both (~42s → ~1.5s on TQ2) because each SearchProperties walks GObjects; the build-693 `walk_class_batch` only got (1) because WalkClass reads one class's struct independently. Don't promise 30× speedups for a batch that doesn't amortise a heavy walk — count what's actually being saved.
- **NEVER batch anything that goes through `Stark::EnqueueInvoke`**. UFunction invokes are serialised on the game thread by design (ProcessEvent must run on the rendering / main game thread). Even a batched API would internally process invokes one-at-a-time, so the "batch" pretends to amortise but doesn't. The `FUNC_Native | FUNC_Static` fast path also runs ProcessEvent per call. Reserve batching for pure-read GObjects walks (search / list / find_refs / walk_class).
- **Build the safety net BEFORE landing the optimisation** (build-693 walk_class_batch lesson). The user flagged it explicitly: "if export sdk if missing something, I also see no out". The optimisation here changes a code path that produces a large file-shaped artifact where a silently dropped class or field is invisible until a user happens to look for it months later. Provability of byte-equivalence between old and new paths needed THREE layers — DLL batch as a trivial `for a in addrs: WalkClassEx(a)` loop (structural guarantee); shared JSON serialiser between single + batch dispatch (`EncodeClassInfoToJson` in Fern.cpp) and shared C# deserialiser (`DumpService.DeserializeClassInfo`); plus a dedicated `WalkClassBatchEquivalenceTests.cs` that runs both consumers through a forced-fallback stub and a happy-path stub against the same 250-class fixture and asserts the outputs match byte-for-byte. Three layers because two would have left room for the bug we couldn't see.
- **Chunk batched fan-outs at ~200 elements**, not "all in one call". A single batch carrying 4000 fully-walked classes produces a multi-megabyte JSON payload and freezes the UI for several seconds with no progress feedback. Chunked-batch keeps progress messages live (one update per chunk = one update per ~1s on a typical game), bounds memory pressure on both DLL and UI side, and gives cancellation a coarse but tolerable granularity (~1s lag). Match the chunk size between the DLL's batch tolerance and the UI's progress-update cadence.
- **Per-chunk fallback to single calls preserves error attribution**. The pre-batch SDK / DumpAll code paths emit a per-class error row (`// ERROR: Failed to walk X` / `kind=error` JSONL) when a single `WalkClassAsync` throws. The batched path can't replicate this because a batch either succeeds wholly or throws wholly. The cleanest preservation is to catch any batch failure (pipe exception OR mismatched element count) and replay that chunk as N single calls — each of which can fail independently with the same error-row emit as before. This keeps the new path strictly behaviour-equivalent to the old path on the failure paths users care about.
- **`-Target Test` is NOT a DLL compile check** (build-697 relapse of the build-656 "verify dist before user test" lesson). The C# xUnit tests stub `IDumpService` and never load the real `UE5Dumper.dll`; the C++ self-tests (`utf8_helpers_test`, `dll_helpers_test`) are isolated binaries built from a handful of leaf source files (Renge / Scharf), not from the full DLL source set. So a green `-Target Test` run can co-exist with a broken main DLL whose `.cpp` files don't even compile, because Ninja's incremental cache happily reuses the last successful `.obj` files and the test pipeline never asks for fresh ones. Caught in the wild build-697: I qualified `ClassInfo` as `Ubel::ClassInfo` in the new `walk_class_batch` work, never noticing it was wrong because the struct sits at *global* scope in `Ubel.h` (not inside `namespace Ubel`); every `-Target Test` was green because none of my changes invalidated the cached main-DLL `.obj` files, and the `-Mode Publish -Clean` build was the first thing to rebuild Aura.cpp / Mimic.cpp / Frieren.cpp / Genau.cpp / Ubel.cpp / Fern.cpp from scratch — all six failed with `'ClassInfo': 並非 'Ubel' 的成員`. **Rule**: any time DLL headers (`*.h`) change, also run `-Target All` (full rebuild including the proxy targets which need the source set too) before committing. Sanity check: look at `D:\Github\UE5CEDumper\dist\UE5Dumper.dll` modification time — if it's older than the most recent commit touching DLL code, the dist DLL is stale and tests may have used a cached binary.

- **A DLL-side "unknown" sentinel must be translated at the WIRE boundary, not shipped raw** (build 2311). `Stark::MsSinceLastHookFire()` returns `UINT64_MAX` for "the PE hook never fired — liveness unknown", which is a perfectly good in-process convention. Putting it on the pipe as-is broke the whole Diagnostics card, because `UINT64_MAX` (18446744073709551615) does not fit an `Int64` and every signed-integer JSON reader rejects it. The wire is a narrower type system than C++: **map sentinels into the range the other side can parse** (`-1` here) before serialising. Note that "never fired" is the *normal* state on a fresh connection — the hook installs lazily on the first invoke — so this was not an edge case, it was the default path.
- **`System.Text.Json` reports OUT-OF-RANGE and FRACTIONAL with the identical message**, and it names neither cause: *"An element of type 'Number' cannot be converted to a 'System.Int64'"*. Reading that, you go looking for a stray decimal point; the actual value was an unsigned 64-bit sentinel. When this message appears, **grab the raw payload before theorising** — the UI's own pipe log (`%LOCALAPPDATA%\UE5CEDumper\Logs\<game>\pipe-0.log`, `Pipe RX:` lines) has the exact bytes, and it took one grep to see `"ms_since_last_fire":18446744073709551615` after several minutes of reasoning about which field might be a double.
- **Telemetry reads must degrade, never throw** (`Services/JsonNum.cs`). One unexpected field blanked an entire diagnostics panel — a panel the user had opened to debug something else. A wrong number in one cell is strictly better than no panel. Use the saturating `JsonNum.L/I/D/B` helpers for any payload whose numeric ranges you do not fully control; keep strict `GetValue<T>` only where a bad value genuinely must fail loudly. The same rule is why `JsonNum.D` collapses non-finite values: a `NaN` that reaches a format string prints "NaN%" at the user.

## DLL Cancellation / Shutdown (build 936)

- **The pipe server is single-connection + synchronous** (`nMaxInstances=1`; one command processed to completion before the next is read). A long scan therefore **blocks the pipe thread**, and the client disconnecting can't be noticed until the handler returns (the thread is in `DispatchCommand`, not `ReadFile`). Consequence: you can't send a "cancel" on the *same* pipe to interrupt an in-flight scan — the in-flight command is holding the line. Cancellation has to be **cooperative** (a flag long loops poll) plus an **out-of-band disconnect signal**.
- **"Game won't close" = a thread join blocked on a long op.** Disabling the CE script calls `UE5_Shutdown → Fern::Stop()`, which **joins the accept thread**. If that thread is mid-scan, the join waits for the scan. Fix: `Cancel::RequestShutdown()` (sticky flag) is set **before** the joins, so in-flight loops bail and the join returns fast. Always set abort flags before joining worker threads, never after.
- **Detect client disconnect with `PeekNamedPipe`, but only while the handler is CPU-bound.** A monitor thread peeks the in-flight pipe handle every ~200ms; a closed client end surfaces as `FALSE + ERROR_BROKEN_PIPE`. Safe because it peeks **only while `m_commandInFlight`** — during `DispatchCommand` the accept thread isn't touching the handle (no concurrent `ReadFile`/`WriteFile`). `PeekNamedPipe` is non-destructive and harmless even on a stale/closed handle (returns an error, no crash), so the close-race during `Stop()` is benign.
- **Cover parallel scans centrally, not per-body.** All `ParallelGObjectsScan` callers already poll a shared `deadlineHit` flag in their stride check; a tiny watcher thread inside `ParallelGObjectsScan` that flips `deadlineHit` on `Cancel::Requested()` makes every parallel scan cancellable with **zero edits to the scan bodies**. Reuse an existing bail path instead of threading a new parameter through every loop.
- **Don't add hard timeouts to ops that are meant to run to completion.** Full SDK dump (`WalkClassesBatch`) can legitimately take a long time; a deadline would silently truncate a real dump. The cooperative cancel (disconnect / shutdown) already stops it when the user actually leaves — that's the case that matters. Bound *discovery* scans with deadlines; let *export* ops finish.
- **A connected cooperative cancel can't interrupt the DLL mid-scan** (single pipe). The Value Search Cancel button abandons the UI-side wait immediately; the DLL finishes the current scan at its own deadline (≤15 s, usually sub-second) and the orphaned response is discarded by the read loop (id no longer pending). Acceptable because the deadline bounds it; near-instant abort only happens on real disconnect (monitor) or shutdown.

## UI / Avalonia

- **`JsonArray.Add(x)` needs an explicit `(JsonNode)` cast or the Native-AOT publish fails** (build 2329). Without it, overload resolution picks `JsonArray.Add<T>(T)`, which carries `RequiresUnreferencedCode` + `RequiresDynamicCode` → `IL2026` / `IL3050`. The cast selects the non-generic `IList<JsonNode?>.Add`. Every other `JsonArray.Add` in `DumpService.cs` already had the cast; a new one written without it compiled and unit-tested fine and only broke at `-Mode Publish`. **`-Target All` / `-Target Test` do NOT catch this** — they build the untrimmed Release assembly, where the attributes are merely advisory. Run `-Mode Publish` before claiming a UI change is done, and treat any new `JsonArray.Add` / `JsonValue.Create` as suspect until it has.

- **DataGrid column sorting needs an explicit `SortMemberPath` under compiled bindings** (build 933-934). This project sets `AvaloniaUseCompiledBindingsByDefault=true`, and Avalonia DataGrid does **not** auto-derive a column's sort path from a compiled `Binding` — so without `SortMemberPath` **no column sorts**, text or template. This presents as "sorting is broken everywhere" and is easy to misattribute to AOT/trimming; it is NOT (it reproduces on the non-AOT build). Fix: set `SortMemberPath="<Prop>"` on every sortable column (use the **numeric backing** property for hex offset/size/score columns so order is numeric, not lexical), and `CanUserSort="False"` on action/button columns. Any new DataGrid must do this.
- **Don't bind a DataGrid `ItemsSource` to a non-generic `DataGridCollectionView` under compiled bindings.** The compiled column bindings infer the row item type from a *generic* `ItemsSource` (e.g. `ObservableCollection<T>`); a non-generic `DataGridCollectionView` erases that → `AVLN2000: Unable to resolve property ... on type <ViewModel>` at build. For client-side filtering, keep the bound collection a typed `ObservableCollection<T>` and rebuild it from an unfiltered backing list (Value Search `FilterText` → `ApplyFilter`), rather than wrapping it in a view.
- **`TextBox.Watermark` is obsolete in Avalonia 12 — use `PlaceholderText`** (warnings-as-errors will fail the publish otherwise).
- **`[DllImport(ExactSpelling=true)]` on a Win32 function that has A/W variants must name the `…W` entry point — the bare name does not exist** (Teleport cursor-hotkey CTD, build 1037). `user32.dll` exports `GetMessageW` / `PostThreadMessageW`, NOT bare `GetMessage` / `PostThreadMessage`; with `ExactSpelling=true` the bare names throw `EntryPointNotFoundException` at the FIRST call. It crashed the app natively (the call was the `while(GetMessage(...))` loop condition on a background thread, outside any try/catch → uncaught bg-thread exception terminates the process). `RegisterHotKey` / `UnregisterHotKey` / `GetCurrentThreadId` have no A/W variant so their bare names are correct — which is why hotkey REGISTRATION succeeded and even logged "bound" before the message loop died. **P/Invoke entry points resolve at RUNTIME, not build** → it compiled and 1385 tests passed while crashing in the real app, because no test called the service. **Rules**: (a) pin `EntryPoint="…W"` for any message/string Win32 fn under `ExactSpelling`; (b) wrap background-thread bodies (esp. a native message loop) in try/catch so a stray exception degrades instead of killing the process; (c) add a platform-gated smoke test that ACTUALLY invokes new P/Invoke (a test that passes `null` for the service never exercises the imports).
- **`ManualResetEventSlim.Dispose()` is not thread-safe vs `Set()`** (same build 1037). A `using var ready = new ManualResetEventSlim()` in a ctor that starts a worker which calls `ready.Set()` races: the ctor's `Wait()` returns the instant `Set()` signals, then the `using` disposes while the worker is still inside `Set()` → undefined / crash. Make it a field and dispose in `Dispose()` AFTER `Thread.Join()`, so the worker is fully done. (Was a latent bug found while chasing the entry-point CTD above — not the actual crash cause, but real.)
- **A UI button that depends on cursor position is meaningless** (Teleport cursor teleport). Clicking a UI button moves OS focus to the dumper window, so the GAME's cursor position is stale/over-the-UI. The only usable trigger for "teleport to cursor" is a system-global hotkey (`RegisterHotKey`) the user presses while the game is focused. Same applies to any feature that reads in-game mouse/viewport state.
- **Don't toggle a button-enabling flag from a polling timer** (Teleport auto-refresh flicker). The 0.5s pose-refresh poll set `IsBusy=true/false`, and the marker/action buttons bound `IsEnabled` to `CanOperate = IsConnected && !IsBusy` → every poll flickered them disabled→enabled twice a second. Give the background poll a "quiet" path that does NOT touch the busy flag; reserve `IsBusy` for user-initiated operations.
- **CE `createHotkey` from an injected Table Lua bundle is unreliable across CE setups** (Teleport, build 1037 — user report). A generated Lua bundle that binds save/recall via `createHotkey` worked on some games' CE sessions and silently did nothing on others. Don't rely on CE-side Lua hotkeys as the primary path; bind global hotkeys from the dumper UI itself (`RegisterHotKey`), with key-capture so the user picks the combo. The CE momentary AA records (one per action, user binds CE record hotkeys) remain a fine secondary path.
